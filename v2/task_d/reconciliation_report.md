## 0. 結論（先出し）

- **0.133（`Limbus_Retention_Reanalysis.md` §4.3記載の相対RMSE）と現行 `core.py` の 0.130457（今回の再現実行値。既知帯0.1305〜0.1314内）の差 0.002543 のうち、約74%（0.001881）を「目的関数における重み付け構造の違い」で説明できた。** BOUNDSの違いはほぼ寄与しない(約6%)。残り約26%(0.000662)は原因を絞れず未解明(主因候補: 曜日調整スクリプトが原本アーカイブに現存せず正確な再現不能)。

- 原本スクリプト(`prep.py`/`model.py`/`stack.py`/`validate.py`)は現行環境で**逐語実行不可能**(後述)。そのため「原本の目的関数・BOUNDS・ridge・アンカー組み込み方式を現行データ上に忠実に再実装して数値検証する」という代替手段(静的比較を超える数値的再現)を採用した。この手法選択は**データ制約による強制**である(逐語実行がそもそも技術的に不可能なため)。
- stock/base回帰子の定義式は §4 に数式で整理した。

### 3.1 境界張り付きの明記(自己チェック必須事項)

- **E0(現行baseline)**: `c`が探索上限**1.0ちょうど**、`log(tau)`が探索上限**log(6000)ちょうど**に一致。`v2/task_a/task_a_summary_raw.json`にも既出記録あり(本レポートで再確認)。
- **E2(原本再現、最良解)**: `log(lam)`が原本BOUNDSの**下限log(1.5)ちょうど**に一致(**新規発見**)。`c`が上限0.999(実験上のソフト上限、真の物理上限1.0に極めて近い)。`log(tau)`が上限log(6000)ちょうど。**3パラメータ中2つ(c, tau)は現行core.pyと同じ境界に張り付き、1つ(lam)は原本固有の境界張り付き。**
- 原本`model.py`の初期値`STARTS`および`validate.py`のpolish始点(`z0 = [log(1.683), log(0.301), ...]`)は、**いずれも原本の最終報告値(λ₁=1.50, k₁=0.30, p=0.023, c=0.90, τ≈6000, h=2.23)に極めて近い**。とりわけ`validate.py`のpolish始点は事実上「答えに近い値から始めて仕上げただけ」に近く、複数始点間の値の幅が小さいことは原本の解が真に安定していることの証拠にはならない(境界張り付き+ほぼ答えを知った上での始点選択の組合せの可能性がある)。
- E2実験のうち6始点中、λが探索下限1.5にほぼ張り付いたのは6/6中4始点(start0,2,3,4,5)、`log(tau)`が上限6000に張り付いたのは6/6中4始点。**多始点間の値の幅が小さいのは境界張り付きによる見かけの安定であり、安定性の証拠として扱わない。**

### 3.2 意外な副次的発見: 埋め込み型アンカー制約は単純に「重みを弱めた」だけではない

現行core.py(E0)は原本再現(E2)よりCCU相対RMSEが低い(0.1305 < 0.1323)**だけでなく**、アンカー(2026年1月DAU/MAU実測)への適合も同時に優れている:

| | DAU誤差% (対360,639) | MAU誤差% (対792,250) | CCU rel_rmse |
|---|---|---|---|
| E0(現行core.py) | **−0.98%** | **+0.16%** | **0.130457** |
| E2(原本再現、最良解、DAU=344,930/MAU=798,027) | −4.36% | +0.73% | 0.132338 |
| E2(6始点全体のレンジ、参考) | −9.45%〜−4.02% | +0.55%〜+2.75% | 0.132195〜0.132920 |
| 原本報告値(`Reanalysis.md`) | −4.6% | +0.5% | 0.133 |

E2最良解のアンカー誤差(DAU −4.36%/MAU +0.73%)は原本報告値(DAU −4.6%/MAU +0.5%)にかなり近く、CCU rel_rmse(0.1323 vs 0.133)と合わせて本再現が原本の挙動を概ね捉えていることを裏付ける。

現行core.pyの「DAU_jan/MAU_janの絶対値を直接NNLSシステムに埋め込む」設計は、原本の「'a'をアンカー非依存で解いてからθ側に重い事後ペナルティ(31倍等)をかける」設計に比べ、**CCU適合とアンカー適合を同時に改善するパレート改善**になっている。これは単なる重みの強弱の違いではなく、アンカー情報を'a'(流入振幅)自体に直接反映させる方が、θ(保持カーネル形状)だけを調整してアンカーに近づけようとするより効率的であることを意味する。**`core.py`が`Limbus_Retention_Reanalysis.md`の文章記述(「1/y重み付き、事前分布として実装」)を忠実に再実装する過程で、原本コードにあった重い事後ペナルティ(31倍・100倍・10倍)を採用しなかったことが、結果的により良いモデルを生んだ**と言える。これは「事後の手法選択によるRMSE改善」ではなく、「原本コードの数値ではなく原本の文章による方法論記述に忠実に従った結果、副産物として生じた改善」である(核心的相違点はcore.pyのdocstring通り"reimplementation from Limbus_Retention_Reanalysis.md"であり、原本コードそのものの逐語移植ではない)。

## 4. stock/base 回帰子の定義式抽出(後半の素材)

### 4.1 base(定数流入)列 — `core.py` `build_X()` / 全タスク共通

```
R(d) = (1-p)·exp(-(d/λ)^k) + p·c·exp(-d/τ)   [d≥1, R(0)=1 に特例設定]   ... core.py: R_kernel()

base_col(t) = Σ_{i=0}^{t} R(i)     for t = 0..T-1                          ... core.py: build_X(), col0 = cumsum(R)
```

- `base_col`は「t=0以降、毎日1人ずつ定常的にactivate(新規/復帰)し続ける」という単位定常流入をR(d)で畳み込んだ累積応答。NNLSはこの列の係数`a[0]`(= `base_per_day`、`report()`が返す`base`または`base_per_day`)を解く。単位は「1日あたりの定常流入人数」。
- Limbusの実データでは`base_per_day → 0`に縮退する(`Reanalysis.md` §4.2: 隔週の無ラベル大型更新49件と共線)。

### 4.2 stock(左打ち切り補正)列 — `task_c.py` `TaskCFitter._design()`(Limbus単独baselineには存在しない、taskC限定)

```
stock_col(t) = exp(-t/τ)     for t = 0..T-1        ... task_c.py: _design(), 条件: use_stock=True の場合のみ列を追加

Xfull(t) = [ base_col(t), event_col_1(t), ..., event_col_N(t), stock_col(t) ]   (use_stock=True時)
Xfull(t) = [ base_col(t), event_col_1(t), ..., event_col_N(t) ]                  (use_stock=False時、PoE2)
```

- `stock_col`は保持カーネルの長期成分と**同じτ**を共有する生の(畳み込みされていない)指数減衰であり、「観測窓開始時点(t=0)に既に存在していた人口」がτの速度で減衰していく寄与を表す。SteamDBの観測開始が実際のタイトルローンチより後(左打ち切り)であるタイトル(WarThunder/FF14/RimWorld/Warframe/DbD/PoE)にのみ追加され、観測不能な「本当のローンチパルス+それ以前の蓄積コホート」を代理する。PoE2は観測開始=実ローンチ(2024-12-06)のため追加されない。
- NNLS係数`a[-1]`(= `report()`の`stock`)は「t=0時点で既に存在していた人口サイズ」の推定値(単位: 人、他のイベント振幅と同じ単位系)。
- 加えて`burn_in=90`日は損失計算の行から除外(`solve()`の`rows = Xfull[bi:] * ...`)されるが、カーネルR自体・`report()`の予測系列は全長T のまま(打ち切りは損失関数の行選択のみに作用し、カーネルの定義には影響しない)。

### 4.3 目的関数への入り方(共通形)

```
mult(t) = (h/24) · (1 + β·g(t))          [task_c.pyは β=0 固定]
rows(t,:) = Xfull(t,:) · mult(t) / y(t)         (burn_in以降の行のみ、task_cの場合)
rhs(t) = 1
a = argmin_{a≥0} || rows·a − rhs ||²            (scipy.optimize.nnls)
loss = ||rows·a − rhs||² [+ ((h-2.2)/0.2)²]     (h事前分布のみ、taskCはLimbusのようなアンカー項なし)
pred(t) = (Xfull(t,:)·a) · mult(t)
rel_rmse = sqrt( mean( ((pred(t)-y(t))/y(t))² ) )     (burn_in以降のみ)
```

`base`(=`a[0]`)と`stock`(=`a[-1]`)は、他のイベント振幅`a[1..N]`と**全く同じ非負制約付き線形回帰の係数**として同一のNNLSシステムに入る。両者を区別する構造的な損失項・正則化項は存在しない(taskCにはLimbusのようなアンカー制約もridgeも一切ない)。両者の共線性(`stock_collinearity.py`が調査対象とする、`corr_stock_base`等)は、この単一のNNLSに複数の「τに支配された形状を持つ列」が同居することから生じる幾何学的な問題であり、本タスクではその数理化は執筆・解析側の作業として素材(上記数式)の提供にとどめる。

## 6. 懸念点・申し送り

1. **残差ギャップ26%(0.000662)は未解明のまま。** 曜日調整スクリプトが原本アーカイブに存在しないため、これ以上の追い込みは原理的に不可能(データ制約)。
2. E2/E3の多始点探索はNelder-Mead単独(高速化のため、core.pyのPowell→NM二段方式は不使用)。E0(baseline)のみcore.py本来のPowell→NM手順で実行(83秒/回)。この手法差が最終値に与える影響は個別に切り分けていない(小さいと推定されるが未検証)。
3. §3.2の「パレート改善」の発見は論文や確定レポートに引用する場合、「core.pyの設計が原本より優れている」という価値判断ではなく、「文章記述への忠実な再実装が、たまたま原本コードの重み付けより良い結果を生んだ」という記述に留めるべき(事後的な優劣判断を避ける)。
4. stock/base数式(§4)は監査を経ていない生の抽出結果。共線性の数理化を書く前に、必要であれば独立監査で数式の正確性を確認することを推奨する。
